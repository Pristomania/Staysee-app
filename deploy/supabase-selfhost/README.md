# Supabase на своём сервере: репетиция и будущая боевая сборка

Здесь лежит урезанная версия официальной сборки Supabase для собственного сервера. Взята из `docker/` репозитория supabase/supabase (19.11.2026). Оставлено только то, чем пользуется приложение StaySee:

| Оставлено | Зачем |
|---|---|
| `db` (Postgres, расширения vector и pg_cron) | вся база: беседы, память, лимиты, ночные задачи |
| `auth` | вход, регистрация, письма подтверждения и сброса пароля |
| `rest` (PostgREST) | то, через что сайт читает и пишет в базу |
| `functions` (Edge Runtime) | серверные функции: `staysee-chat` и остальные |
| `kong` | единая точка входа; сайт ходит в неё по адресу `/supabase` |

Убрано (приложение этим не пользуется): панель Studio, Realtime, Storage (файлы), imgproxy, postgres-meta, Logflare, Vector, Supavisor.

Все порты открыты только на `127.0.0.1`. В интернет эта сборка не смотрит, пока мы сами не направим на неё nginx.

## Запустить репетицию (на компьютере с Docker)

```bash
# 1. Выгрузить из боевой базы только СТРУКТУРУ (без данных людей), только чтение:
npx supabase db dump --linked --schema public -f prod-schema-public.sql
# 2. Поднять всё, развернуть эту структуру, прогнать проверки, показать расход памяти:
cd deploy/supabase-selfhost
bash rehearsal.sh all /путь/к/prod-schema-public.sql
bash rehearsal.sh down     # остановить, данные оставить
bash rehearsal.sh reset    # остановить и УДАЛИТЬ данные этой репетиции (только её)
```

Результат прогона 20.11.2026 на компьютере Насти: боевая структура развернулась без единой ошибки, 14 проверок из 14, весь стек в простое занимает около 530 МБ (база 90, Auth 12, интерфейс к базе 46, функции 247, шлюз 135). Данные Docker лежат на диске D (`D:\DockerData`), диск C не используется.

## Главное: файлы миграций НЕ воспроизводят боевую базу

Если применить 95 миграций из `supabase/migrations/` к пустой базе, получится не та схема, что в бою (миграция 025 прямо называет это «prod drift»). Сверка 20.11.2026 (структура боевой базы против базы из миграций):

- `messages`: в бою есть `role`, `user_id`, `updated_at`, которых нет в миграциях; в миграциях есть `content_encrypted`, `encrypted_content`, `encryption_version`, которых нет в бою. Из-за этого приложение не смогло бы записать ни одного сообщения.
- `conversations`: в бою есть `archived_at`, `message_count`, `status`, `updated_at`; политика безопасности одна общая («Users can manage own conversations») вместо четырёх отдельных в миграциях.
- `profiles`: в бою `email`, `plan`, `updated_at`; в миграциях `onboarding_completed`, `primary_concern`.
- Таблица `ai_usage_log` есть только в миграциях; функции `handle_new_user` в бою нет.

Поэтому переезд делается из **выгрузки настоящей базы** (структура + данные), а не повторным прогоном миграций. Миграции годятся только для новых изменений поверх уже развёрнутой базы (`rehearsal.sh mark`, затем `rehearsal.sh migrate`). Отдельно стоит решить, как привести файлы миграций в соответствие с боем (чтобы тестовые базы и будущие разработчики не получали другую схему).

Выгрузка структуры не содержит: два триггера на `auth.users` (согласия при регистрации, тариф нового человека) и четыре ночные задачи `pg_cron`. Они записаны в `after-restore.sql` (проверено по боевой базе, только чтение).

`make-env.mjs` создаёт файл `.env` со свежими случайными секретами. Его нельзя класть в git и показывать. `functions.env` (ключи моделей и переключатели `STAYSEE_*`) в репетиции не нужен: без него функции запускаются, а модель не отвечает.

## Что проверяет `smoke.mjs`

Регистрация и вход, создание беседы и сообщения тем же способом, что и приложение, чужие сообщения не видны (с входом и без), запрос к чату без входа отклоняется, `memory-health-check` открыт без токена (проверяет свой секрет), `staysee-chat` запускается, расширения vector и pg_cron на месте, ночные задачи созданы, таблицы приложения созданы.

## Отличия от облака Supabase, о которых нужно помнить

1. **Проверка токена у функций.** В облаке у каждой функции свой переключатель (`verify_jwt` в `supabase/config.toml`). В собственной сборке роутер один на всех. Поэтому функции, которые проверяют свой секрет (`memory-health-check`, `purge-scheduled-rooms`, `backfill-conversation-summaries`, `auth-email`), перечислены в `FUNCTIONS_OPEN_NAMES`, а роутер `functions-main/index.ts` пропускает их без токена. Это единственная правка в официальном файле. Без неё ежечасная проверка памяти на GitHub получала бы 401.
2. **Адрес.** Сейчас сайт и расписания ходят на `jnxrildlwvtxhtiwucbt.supabase.co`. После переезда этот адрес надо заменить в `.github/workflows/memory-health.yml`, в сайте (`VITE_SUPABASE_URL`) и в скриптах `scripts/`.
3. **Письма.** В репетиции подтверждение почты отключено (`ENABLE_EMAIL_AUTOCONFIRM=true`). На боевом сервере письма идут через функцию `auth-email` (хук отправки писем): нужны `AUTH_EMAIL_HOOK_ENABLED=true`, `AUTH_EMAIL_HOOK_SECRET` и `AUTH_EMAIL_HOOK_URI`. Новая версия Auth (v2.197) **отказывается запускаться**, если адрес хука задан по обычному `http://` внутри сети Docker, поэтому адрес должен быть `https://<наш домен>/supabase/functions/v1/auth-email` (через nginx). Проверяется отдельно, с настоящей почтой.
4. **Настройки входа из панели облака** (минимальная длина пароля, лимиты запросов, срок жизни ссылок, шаблоны писем) в репозитории частично не записаны. Их нужно выписать из панели облака перед переездом и повторить здесь.
5. **Зависимости функций** (`npm:@supabase/supabase-js@2`, `jsr:`) подгружаются при первом запуске. С российского сервера доступность `npm` и `jsr` нужно проверить; после первого запуска они лежат в кэше (том `deno-cache`).
6. **Бэкапы**: в облаке они были встроены, здесь нужно настроить самим (ежедневная выгрузка базы и проверка, что её можно восстановить).
7. **Данные людей** репетиция не переносит: только структура. Перенос боевых данных (беседы, память, вектора, пользователи Auth) это отдельный шаг со своей проверкой, согласованием и временем простоя.
8. **Шлюз Kong** по умолчанию запускает по рабочему процессу на каждое ядро компьютера (на 12 ядрах это 667 МБ). В сборке число процессов задано (`KONG_WORKERS`, по умолчанию 2): 135 МБ.
9. **Расширение vector** стоит в схеме `public` и в бою, и здесь (в выгрузке оно не создаётся само, `rehearsal.sh restore` создаёт его до разворачивания структуры).

## Проверка адреса сервера ДО покупки

Перед тем как платить за сервер на месяц, арендовать его на час-два (почасовая оплата) и выполнить на нём `bash check-outbound.sh`. Скрипт без ключей и паролей спрашивает все внешние адреса, нужные приложению (образы Docker, библиотеки npm и jsr, OpenRouter, Telegram, модели Cloud.ru), и показывает OK или NO. Результат верен только для сети той машины, на которой запущен (VPN на ней искажает картину). Тревожные места на 20.11.2026: Telegram в России ограничен (оповещения об ошибках идут через него), у OpenRouter закрыта оплата из РФ, доступность Docker Hub и npm с российских серверов зависит от хостера.

## Что ещё не проверено

Настоящие письма через хук, нагрузка (несколько одновременных ответов Стейси: каждый занимает до 256 МБ в функциях), доступность `npm`/`jsr` с российского сервера, перенос боевых данных и время простоя, резервные копии и восстановление, настройки входа из панели облака, TLS и nginx перед шлюзом.

## Миграции в будущем

`rehearsal.sh migrate` применяет файлы из `supabase/migrations/`, которых ещё нет в `supabase_migrations.schema_migrations` (как это делает Supabase CLI), и записывает их туда. После переноса настоящей базы историю нужно перенести тоже (или пометить `rehearsal.sh mark`), иначе применятся все 95 заново.
