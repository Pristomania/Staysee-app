# StaySee AI: границы серверных замков бесед

20.11.2026. Продолжение платёжной работы после snapshot096. Это карта проверенного кода и следующий объём работ, НЕ отчёт о готовых замках. Изменения production не выполнялись.

## Подтверждено чтением этой рабочей версии

1. `src/components/screens/MainScreen.tsx:41` загружает `conversations.select('*')`. Нельзя сохранить этот контракт для закрытых строк: таблица содержит summary/metadata. Список должен получать только явно разрешённые поля: id, title, created_at, last_message_at, сведения о доступности/порядке. Названия и даты допустимы по требованию пользователя, содержимое — нет.
2. `MainScreen.tsx:61` вызывает `load_conversation_last_messages`. Миграция063 определяет SECURITY DEFINER, проверяет владение, но не тарифный доступ. Изменение только RLS сообщений не закроет этот путь превью. RPC нужно отдельно ограничить тем же серверным решением доступа.
3. `src/lib/chatMessages.ts` читает сообщения напрямую, включая загрузку старой истории для поиска. Базовая политика024 проверяет владение беседой, а не доступность после срока тарифа. Нужны проверки реальных SQL-запросов от authenticated, не только поддельного frontend-клиента.
4. Триггер087 `enforce_conversation_limit` использует сырой `u.tier` и считает все активные беседы. Snapshot096 сам по себе не изменяет raw tier. Поэтому без обновления триггера создание после expiry и показ списка не согласованы с новым оплаченным сроком.
5. `context.ts:212` читает summary/metadata, а `conversationRetrieval.ts:715+` имеет semantic-ветку с service-клиентом для сообщений. Перед платным вычислением нужен общий серверный guard. RLS пользователя не ограничивает service_role; остановка чтения должна быть явной и до трат. Фактический exploit/production-состояние этой картой не проверены.
6. Альтернативные читатели: ConversationDynamicsScreen, ConversationNotesScreen, MemoryScreen, conversationDynamicsView, progressDiary. Экспорт памяти проходит через `src/lib/memoryV3Viewer.ts` и отдельный серверный обработчик; его нельзя считать защищённым по замку страницы.
7. `PrivacyScreen.tsx:164` удаляет все собственные беседы напрямую. Нельзя случайно превратить платный запрет чтения в запрет удаления данных. SELECT/UPDATE/DELETE и возврат строк PostgREST требуется проверять раздельно.

## Подтверждённые продуктовые условия

- На free после срока тарифа доступна одна верхняя беседа; остальные только название/дата/замок, без чтения/превью/поисковых фрагментов.
- ID доступной беседы фиксируется сервером. Сортировка/смена времени/удаление верхней не должны последовательно раскрывать архив.
- Пакет на free открывает сообщения, но не дополнительные беседы и не платные функции. Ноль сообщений при действующем тарифе не закрывает функции.
- Ручные семейные/unlimited назначения не превращаются в истёкшую покупку. Данные при downgrade не удаляются.
- На expiry клиент очищает уже загруженные закрытые данные из состояния. Внешние ранее сделанные копии отозвать невозможно.

## Следующая реализация — ещё не сделана

Единое серверное решение доступа должно применяться к RLS, безопасному списку, preview RPC, chat guard и альтернативным readers. Простое скрытие карточек или фильтрация в React не подходят. Прямые таблицы должны скрывать содержимое закрытых бесед; safe-list RPC возвращает их допустимые метаданные. Все definer/service пути требуют отдельной проверки. Алгоритмы формирования памяти Claude не менять: координировать только границы чтения и контракт доступа.

Для тестов необходимы: чужой UID, expired purchased без вызова quota, pack-only, paid с quota0, manual/unlimited, прямой REST/RPC, summary и превью, lookup известного закрытого ID, поиск, удаление доступной беседы, expiry между предварительной проверкой и выполнением, гонка создания, неизвестный тариф и смена аккаунта в UI.

## Вопросы, которые нельзя незаметно решить кодом

- При удалении единственной доступной беседы безопасно разрешить новую пустую, не открывая старые. Это инженерное предложение, не утверждённое новое продуктовое правило. Нужен явный контракт счёта архивных/активных бесед: нынешний count всех активных не подходит.
- Premium → basic с ограничением чтения первыми тремя ранее было лишь предложением. Не включать это дополнительно под видом free-замков.
- Ручной порядок относительно следующего сообщения и отдельная выгрузка своих данных требуют сверки с ранее принятыми решениями. Не подделывать last_message_at и не закрывать маршрут удаления.

## Дополнительно подтверждено пользователем20.11

- Если на free удалена единственная доступная беседа, можно создать новую пустую. Старые архивные беседы при этом не открываются. Это теперь утверждённое правило, не предложение.
- Удаление отдельной закрытой беседы доступно без оплаты из её меню в списке. Человек не должен удалять весь аккаунт/всю переписку ради удаления одной архивной беседы. Коммерческий замок запрещает чтение, но не право удалить собственную беседу.
- Приёмка будущих замков обязательно включает удаление одной закрытой беседы: остальные сообщения и беседы не меняются, доступная беседа не переключается на следующую архивную, чужой ID отклоняется, список обновляется только после подтверждённого сервером успеха. Ошибка сети не должна показывать ложное успешное удаление.
