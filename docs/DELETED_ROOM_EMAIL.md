## Поведение

- Подписанное событие Supabase проверяется Standard Webhooks (подпись и срок), затем по user.id читаются только два поля profiles. Email из формы не используется для поиска аккаунтов.
- При удалении: письмо сообщает, что содержимое не восстановить, и называет фактический room_purge_after. Ссылка только на главную, токен сброса не включается. Ранее назначенные даты не меняются.
- Действующая комната, включая старый аккаунт без profiles: обычное восстановление. Ошибка запроса к базе не равна отсутствию строки: письмо не отправляется, возвращается безопасная ошибка.
- Поддержаны signup, recovery, magiclink, invite, reauthentication, email_change (включая два адреса Secure Email Change) и семь уведомлений безопасности. Неизвестные типы отклоняются, а не теряются молча.
- Старые ссылки: экран проверяет удаление до показа формы и повторно перед сохранением пароля. Сбой проверки не допускает изменение пароля.
- Проверка замечаний: уведомление о завершённой смене email направляется на проверенный `old_email`, не на новый адрес. Если прежний адрес отсутствует или некорректен, отправка отклоняется. Уведомления об удалении помечены ID аккаунта; экран восстановления отслеживает выход из сессии и не принимает запоздавший результат проверки старой сессии. Тестируется последовательность «сессия есть → удаление и выход → запрос профиля вернул пустую строку».
- Публичное сообщение после «Забыли пароль?» остаётся нейтральным. Новых правил хранения данных, миграций и восстановления удалённого содержимого нет.

## Подключение — только в таком порядке

1. Сверить включённые Auth email flows в Dashboard. Хук заменяет SMTP целиком, не только recovery. Нельзя активировать непроверенную ветку регистрации.
2. Настя сама вводит в Edge Function Secrets существующие `POSTBOX_SMTP_USER` (ID API-ключа) и `POSTBOX_SMTP_PASSWORD` (секретная часть ключа). Не доставать пароль из маскированного поля SMTP, не печатать и не сохранять в репозиторий.
3. Создать секрет подписи для Send Email hook, безопасно сохранить его как `SEND_EMAIL_HOOK_SECRET` и в настройке хука. Не показывать секрет в отчётах. Функция использует стандартные SUPABASE_URL и SUPABASE_SERVICE_ROLE_KEY.
4. Проверить Deno-сборку, тесты, подписи и SMTP STARTTLS. Затем выложить `auth-email` с `verify_jwt=false`: аутентификация здесь — подпись Standard Webhooks, а не bearer JWT. Сам по себе деплой ещё не включает обработчик.
5. Только после готовности функции включить HTTPS Send Email hook на `https://jnxrildlwvtxhtiwucbt.supabase.co/functions/v1/auth-email`. Email Provider оставить включённым. Публичный сайт — https://staysee.ru; локальные redirect_to из события игнорируются.
6. В пределах отдельного подтверждённого бюджета писем проверить удалённый тестовый аккаунт (письмо без токена), действующий технический аккаунт (обычный сброс) и подтверждение регистрации на одноразовом локальном стенде без новых боевых аккаунтов. Не отправлять ничего реальным/семейным аккаунтам без разрешения. Пользователь сам открывает письма и вводит пароли.
7. Выложить фронтенд после проверок и проверить старую ссылку. Не заявлять готовность по одной зелёной сборке.

Откат: отключить Send Email hook в Auth Hooks; продолжит работать существующий SMTP. Это возвращает и старое поведение восстановления удалённой комнаты — явно отметить в журнале. Не удалять SMTP-конфигурацию, пользователей или даты хранения.

Ограничения: SMTP не предоставляет exactly-once доставки; повтор хука после сетевого таймаута может привести к повторному письму. Дата в письме — запланированная дата из базы, а не доказательство, что ежедневная очистка уже успешно прошла. Изменение пароля напрямую через Auth API вне интерфейса не блокируется этим фронтендом; доступ к удалённому содержимому не восстанавливается.
