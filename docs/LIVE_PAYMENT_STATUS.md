# Проверка оплаты своего заказа —20.11.2026

Добавлен локальный безопасный путь чтения статуса оплаты перед будущим подключением checkout. Возврат из кассы, URL-флаг `success` и наличие номера заказа не подтверждают оплату и не дают доступ.

## Реализация

-101: `get_my_live_payment_status(orderUUID)` доступен только authenticated и привязан к auth.uid(). Чужой/несуществующий заказ, заблокированный или удалённый аккаунт возвращают одинаковый NULL. Гость/service_role не имеют execute. Прямой доступ к закрытому ledger не открывается.
-Usage блокируется первым, как при подтверждении оплаты. Затем возвращаются минимальные поля своего заказа и свежий get_my_billing_snapshot. Чтение не вызывает confirm, grant, reserve или записывающее expire: не тратит сообщения, не подключает/продлевает тариф, не меняет ledger.
-Pending с прошедшим expires_at проецируется как expired без записи; позднее правильно подтверждённая оплата всё ещё может стать applied.
-Исторический месячный paidUntil вычисляется от сохранённого appliedAt. currentGrant=true только если именно этот месячный заказ совпадает с действующим purchased tier, началом и окончанием текущего периода. Старый «Базовый» после повышения не показывается как вновь подключённый, ручной/unlimited доступ не выдаётся за действие этой покупки.
-Купленный пакет после расходования остаётся записью обработанного платежа, а не обещанием новых100 сообщений прямо сейчас. paid_unfulfilled сообщает, что деньги учтены, но услуга требует разбора; повторно платить не предлагает.

Клиентский декодер проверяет ожидаемые UUID пользователя/заказа, структуру, типы, статусы, связь дат и 30дневного периода, свежий snapshot и currentGrant с точностью до микросекунд. Чтение ограничено общими10секундами, поддерживает отмену и проверяет сессию до и после ответа. JWT прикреплён к запросу явно; userId не передаётся в SQL как параметр авторизации. HTTP-ответ ограничен2МБ и строгим UTF8. При завершении любого запроса собственный AbortController отменяется: зависшее тело500-ответа не продолжает загрузку после ошибки. Нет вечного polling, provider/service-role секретов в браузере, записи прав из URL или выдачи доступа в PlanContext.

`browserLivePaymentStatusApi` подготовлен, но **ещё не подключён к покупке/странице возврата**, чтобы не имитировать готовый checkout. Новая Edge Function не нужна: это self-only RPC через штатный PostgREST. Покупка и касса не включались.

## Независимое ревью и решения

Критических проблем не обнаружено. Оба Important воспроизведены и исправлены в один проход: неотменённое тело ошибочного HTTP-ответа; расчёт30дней с разными DST-часовыми поясами. В тесте ожидалось720часов, получалось719.101 теперь задаёт UTC как для своего чтения, так и для SQL confirmation: срок согласован и не меняется с часовым поясом сессии. Этот ALTER FUNCTION сохраняет search_path/ACL; не менять только reader без settlement boundary.

До боевой выкладки проверить: старые реальные заказы, если они существуют, должны были выдаваться в UTC. Для исторических периодов, выданных по другой календарной timezone, нужен авторитетно сохранённый конец периода, а не угадывание из appliedAt. Здесь не выполнялось ретроактивное исправление каких-либо боевых заказов.

Два небольших замечания отложены до подключения UI: старый formatter карточки может округлить активный остаток меньше1миллисекунды до надписи о завершении; UUID с верхним регистром допускается входной проверкой, но требует нормализации перед сравнением с lowercase SQL. Ни экран оплаты, ни потребитель прав сейчас не подключены; не считать эти мелочи уже закрытыми.

Продолжение20.11: оба замечания закрыты в [этапе проверки условий покупки](PURCHASE_REVIEW.md), с двумя наблюдёнными RED→GREEN регрессиями. Это не включает live UI или платежи.

Решения исполнителя: использовать self-only RPC вместо нового привилегированного HTTP-сервиса; продолжить локально без коммита/выкладки; единый UTC на read+confirm. Цена решений: checkout ещё не подключён, файлы пока только в рабочей ветке, исторические не-UTC выдачи требуют отдельной миграционной проверки. Боевой provider, реальная конкуренция PostgreSQL и свежесть уже отрисованного UI остаются условиями внешней приёмки, не выводом из локального GREEN.

## Что дальше

После этого нужен live checkout со снимком цены/чека и подключённой страницей серверной проверки результата, согласованная фискальная схема, тестовая приёмка реальной Робокассы, затем отдельно разрешённая выкладка. Реальные деньги, магазин, секреты и аккаунты этим локальным этапом не трогались; коммит/публикация не выполнялись. Не переносить технический пример чека из тестового checkout в production автоматически.
