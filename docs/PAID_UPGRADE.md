# Повышение тарифа — локальная реализация20.11.2026

## Согласованное правило

Из действующего купленного «Базового» можно перейти на «Премиум»:

- Полная серверная цена Premium:4900₽. Зачёт/возврат остатка «Базового» не добавлен.
- После подтверждения оплаты один текущий тариф заменяется на Premium, начинается новый срок30дней.
- Включённый остаток «Базового» прекращается. Новый лимит ровно1000 сообщений Premium, не1000+остаток прежнего тарифа.
- Отдельно купленные сообщения сохраняются с прежними остатком и сроком. Они расходуются после включённого лимита, не продлеваются при повышении и не превращаются во включённые сообщения.
- История первой оплаты сохраняется, бесплатные50 повторно не появляются.

Полную цену/новый срок пользователь подтвердил отдельным ответом. Пользователь называет младший тариф «Стандарт»; текущий код и опубликованный каталог используют имя «Базовый»/`basic`. Переименования тарифа этим этапом не делаем.

## Что изменено

Миграция `20261120210000_105_paid_upgrade.sql` меняет два определения: `create_billing_live_order` и `confirm_billing_live_order`, и добавляет в закрытый ledger `purchase_kind` (new_period/upgrade). К прежним ограничениям добавлено одно исключение: текущий активный **купленный** basic→premium, без unlimited. Состояние проверяется ещё раз под блокировкой при подтверждении, а не только по снимку на экране. Цена/сумма заказа остаются серверными, фактическое начисление — через проверенный ResultURL, не через возврат покупателя на сайт.

Создание заказа ничего не включает. Повтор с тем же ключом возвращает прежний заказ; повтор подтверждения не продлевает срок и не сбрасывает потраченные сообщения. Продление того же активного тарифа и переход вниз до его окончания по-прежнему не предлагаются. После истечения можно купить обычный новый период. Ручные/семейные/unlimited планы не переклассифицируются как оплата.

Если после создания заказа человек удалён/заблокирован или ему уже включили Premium/ручной тариф, подтверждение учитывает реальные деньги как `paid_unfulfilled`, не заменяя права. Поздняя оплата «Базового» не понижает Premium. События требуют ручного разбора/возврата по отдельному процессу — автоматических возвратов нет.

Ожидающее повышение сохраняет намерение `upgrade`: если администратор вручную перевёл Basic даже на Free, callback не отменит это решение. Это не запрещает обычную первую покупку на Free (`new_period`) или подтверждение повышения после естественного истечения купленного Basic. Существующие заказы, которые создавались до100 без возможности повышения, получают значение new_period.

Срок в подтверждении уже берётся после usage/order locks (099). В создании заказа100 также использует post-lock wall clock: начало длинной транзакции не заставит считать уже истёкший тариф активным. Создание/истечение заказа записываются явно от того же времени после ожидания; на оплату остаётся полный час.

Тестовые SQL-fixtures применяют095–100 по порядку; устаревшее повторное применение099 после100 убрано, чтобы тесты не скрывали новое поведение.

## Проверки

```powershell
node --import tsx --test scripts/paid-upgrade.dbtest.mjs
node --import tsx --test scripts/paid-upgrade.dbtest.mjs scripts/robokassa-live-result.dbtest.mjs scripts/conversation-archive-access.dbtest.mjs scripts/conversation-creation-expiry.dbtest.mjs scripts/paid-access.dbtest.mjs scripts/billing-snapshot.dbtest.mjs
npm run test:offline
```

Фокусные13 SQL-проверок прошли. Сначала7 из9 воспроизвели прежний запрет повышения; после100 прошли все. Дополнительный тест истечения тарифа внутри транзакции воспроизвёл старый отказ при now(), post-lock clock устраняет его. Реальные SQL проверяют цену490000коп.,30дней, новый лимит1000 и переход на купленный пакет только после его исчерпания, сохранение всех полей пакета/истории, повтор, downgrade/действующийPremium/ручнойплан/unlimited, удаление/блокировку, права RPC. Команды не читают env, не используют внешние БД или платные API.

Независимое ревью: критических проблем не найдено. Два важных замечания воспроизведены и исправлены за один проход: полный срок checkout от post-lock времени и уважение ручного снятия тарифа при ожидающем повышении. Тесты сначала вернули неправильный created_at и applied вместо отказа; после исправления13/13 прошли, включая положительные сценарии первого Free и естественного истечения. Старый финансовый тест, ожидавший отказа в повышении, обновлён под явно выбранное новое правило, а не скрыт. Повторного ревью не проводилось.

Небольшое замечание оставлено: общие тестовые fixtures через existsSync пропускают отсутствующие099/100 и тогда обнаруживают проблему поведением, а не сразу настройкой. Это не влияет на продукт, но до запуска нужно сверить весь инвентарь миграций.

Финальная проверка: **63/63 SQL**, включая прежние деньги/архив/ResultURL и13 новых сценариев повышения; **2824/2824 offline** (1487+45+411+881), `typecheck` и `git diff --check` успешны. Новый Deno callback и сборка с фиктивным публичным ключом прошли в предыдущем локальном этапе; после этого frontend/TS-runtime продукта не менялись. Незавершённые первые попытки offline с ошибкой записи лога не засчитывались: повторный полный `npm run test:offline` без большого файла лога завершился успешно. Get-PSDrive показал3,5ГБ свободного C, очистка чужих файлов/кэшей не выполнялась.

Решения исполнителя: полный текущий прайс без изобретения зачёта/возврата; все общие SQL-проверки применять к актуальной цепочке095–100; старый запрет повышения в тесте заменить новым согласованным ожиданием; добавить закрытый признак намерения заказа, поскольку одного текущего tier недостаточно. Цена решений: нет пропорционального расчёта, сравнивать нужно новые тесты, а выкладка требует дополнительной колонки/порядка миграций. Внешняя приёмка и настоящие параллельные соединения не подменяются PGlite.

## До реальной оплаты

Изменения только локальные; сайт, данные людей, ключи и магазин не менялись, покупка не включена. Этот этап не заменяет live checkout, фискальную схему, возвраты и приёмку провайдера из [отчёта ResultURL](ROBOKASSA_LIVE_RESULT.md). В будущем checkout обязан явно написать: полная цена Premium, новые30дней, старый включённый остаток не переносится, докупленные сообщения сохранены. Сейчас за пользователя ничего не списывалось.

PGlite не моделирует несколько независимых PostgreSQL-сессий и боевой PostgREST; их проверка остаётся условием запуска. Перед объединением с параллельной веткой Claude сверить новые номера099/100 и не выкладывать095 отдельно.
