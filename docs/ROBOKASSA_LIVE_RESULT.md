# ResultURL Робокассы: локальный этап, 20.11.2026

## Что добавлено

Отдельная Edge Function `robokassa-live-result`, изначально выключенная. Она принимает только серверный POST ResultURL, проверяет SHA256 с отдельным live паролем №2 **до чтения базы**, затем сверяет сохранённые магазин, режим, номер и сумму заказа. Вызывает только закрытую SQL-функцию `confirm_billing_live_order`. Страница успеха ничего не начисляет. Тестовые обработчики не изменялись и не вызывают live выдачу.

Исходная сумма используется для подписи без переформатирования (включая шесть десятичных знаков); копейки считаются целыми числами. Подделки, test режим, дубли полей, неверный UTF8/percent encoding, чужие Shp-поля, иной магазин или сумма отвергаются. Нет записи email/тела запроса. Максимум 8192 байта, 24 поля, общий срок обработки 10 секунд с отменой HTTP-запроса к базе. Ответы без CORS, с no-store.

`OK{InvId}` возвращается только после учтённой оплаты: `applied` либо `paid_unfulfilled`. Повтор не выдаёт тариф или пакет снова. Если SQL успел зафиксировать оплату, но ответ потерян, следующий callback получает прежний результат. Отключение создания новых заказов не мешает подтверждать уже оплаченные.

`paid_unfulfilled` — **не выданная услуга при учтённой оплате**, например удалённая комната, блокировка или уже действующий/ручной тариф. Выводится безопасное структурированное событие `robokassa_live_paid_unfulfilled` с номером заказа, кодом причины и признаком повтора. Перед запуском нужен человек/процесс, разбирающий такие случаи и возвраты: автоматического возврата нет. Сбой логирования не отменяет подтверждение уже записанных денег.

Миграция `20261120200000_104_live_confirmation_clock.sql` заменяет только определение времени в confirm из095: после блокировок строк берётся `clock_timestamp()`. Регрессия воспроизвела отказ `active_plan` после реального истечения тарифа внутри старой транзакции; после исправления новый тариф выдаётся на полные 30 дней. Историческая095, каталог, финансирование пакетов и права RPC сохранены.

## Проверки

Команды не читают env-файлы, не обращаются к настоящим пользователям/Робокассе и не расходуют деньги:

```powershell
node --import tsx --test supabase/functions/_shared/robokassaLiveResult.cases.test.ts scripts/robokassa-live-store.test.ts scripts/robokassa-live-result.dbtest.mjs
npm run test:offline
node --import tsx --test scripts/robokassa-live-result.dbtest.mjs scripts/conversation-archive-access.dbtest.mjs scripts/conversation-creation-expiry.dbtest.mjs scripts/paid-access.dbtest.mjs scripts/billing-snapshot.dbtest.mjs
npm run typecheck
deno check --node-modules-dir=none supabase/functions/robokassa-live-result/index.ts
```

Фокусные 58 проверок: 46 протокол/HTTP, 7 реальный Supabase SDK с offline fetch, 5 реальный SQL через PGlite. Подписи в тестах независимо вычисляет node:crypto. SQL покрывает тариф, пакет, повтор, отключение новых заказов, недоступный аккаунт, потерянный ответ после commit и истечение старого тарифа. PGlite не доказывает конкуренцию двух настоящих PostgreSQL-сессий или работу боевого PostgREST/gateway.

Итог общего прогона: **2824/2824 offline**, **50/50 SQL** (новые5 + прежние45), `typecheck`, новый Deno entrypoint и сборка с фиктивным публичным ключом — успешно. В сборке остаётся прежнее предупреждение о чанках больше500КБ, это не ошибка сборки. Протокол/адаптер и регрессия времени проверены RED→GREEN; асинхронный сбой логирования отдельно сначала воспроизведён и затем устранён.

## Независимое ревью

Критических ошибок начисления не найдено. Исправлены:415 на законный charset="UTF-8" и включение обработчика с паролем из одних пробелов. Оба дефекта воспроизведены тестами до правок. Усилены проверки повреждённого UTF8: теперь испорченное необязательное поле добавляется к правильно подписанному конверту; временное ослабление декодера привело к трём ожидаемым падениям, строгая версия проходит.

Два небольших замечания оставлены: Fee/fee не считаются регистровым дублем, поскольку это игнорируемые метаданные (защищённые поля/все Shp проверяются строго); offline ответ PostgREST в тесте SDK использует объект/null, а не массив. Ни то ни другое не даёт права на тариф; настоящее поведение gateway/PostgREST остаётся обязательной приёмкой до запуска.

Решения этого этапа: сначала callback без включения покупки из-за незавершённой фискальной схемы; выполнение локально без коммитов/выкладки и без повторных согласований каждого технического шага; узкий транспортный интерфейс Supabase вместо чрезмерно рекурсивных generic-типов Deno, с проверкой ответов во время выполнения. Цена этих решений: этот этап сам по себе не позволяет покупать; доказательства пока только в рабочей ветке; типизация схемы слабее, чем с полным generated schema. Боевой provider/gateway, многосессионная БД, чеки/возвраты явно не проверены — локальные тесты не заменяют эти условия запуска.

Сборка для проверки использует только явно заданные фиктивные публичные параметры. Полученный `dist` не предназначен для выкладки. Старые ошибки общего Edge-графа памяти не исправлялись в этом этапе: его ведёт другой агент/пользователь; собственный новый платёжный граф проверяется отдельно.

## Что необходимо перед реальными деньгами

Сейчас **нет live checkout и включённой кнопки покупки**. На сервер ничего не выложено, настройки магазина и секреты не менялись. Не считать этот этап запуском оплаты.

1. Утвердить фискальный сценарий/чеки, описание услуги и сроков, документы/согласие для рекуррентов, если они будут. Тестовый пример чека не переносить в production автоматически.
2. Реализовать live создание checkout со снимком чека и цены, авторизацией/защитой повтора и экраном серверно подтверждённого результата. Не включать оплату на одном callback.
3. Отдельно настроить магазин на SHA256, HTTPS ResultURL POST и точные `Shp_mode=live`, `Shp_shop=<магазин>` во всех live заказах. Этот обработчик не JWS ResultUrl2, не автоподписка и не холд.
4. В серверном окружении понадобятся **имена, не значения**: `ROBOKASSA_LIVE_RESULT_ENABLED` (только точное `1`), `ROBOKASSA_LIVE_MERCHANT_LOGIN`, `ROBOKASSA_LIVE_PASSWORD_2`, штатные `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`. Пароль №1 здесь не используется. Если live пароль №2 совпадает с любым доступным test паролем, функция откажет. Отсутствие test env не доказывает независимость ключей: вручную проверить перед запуском. Не помещать секреты во frontend.
5. При отдельном разрешённом развёртывании применить миграции по порядку, развернуть callback с отключённой JWT-проверкой gateway (provider не пользователь Supabase). При этом собственная проверка подписи остаётся обязательной. Этот шаг **не выполнен**.
6. До включения проверить полный test путь, затем согласованный минимальный реальный платёж, повтор, восстановление после сбоя, правильные квоты/срок/чек, возврат и сообщения клиенту. При переносе не сбрасывать sequence InvId и историю заказов.
7. Настроить наблюдение за неисполненными оплаченными заказами, убедиться, что выключение создания заказов не выключает уже нужные callback. Подтвердить конкурентные сценарии на локальном полноценном PostgreSQL.
