# StaySee AI: первый тестовый платёжный backend

## Что реализовано

Отдельный тестовый журнал заказов, серверные цены, SHA256-подпись формы с Receipt, проверка уведомлений и идемпотентное завершение тестового заказа. Авторизованный пользователь читает только собственный статус через проверенный обработчик. Таблица целиком закрыта от authenticated/anon, включая прямой REST. На запросы создания/статуса действует список разрешённых тестовых аккаунтов; нежелательные Origin отклоняются. Повтор использует сохранённые цену и точный Receipt, а не сегодняшний каталог.

**Это не включённая оплата приложения.** Код не выложен, миграция не применена, кнопки приложения не изменены, секреты не созданы и не прочитаны. Успешный тестовый заказ имеет `status=test_paid`, `grantsAccess=false`. Он не меняет тариф, счётчики, память и признак прежней покупки. Настоящие покупки и рекуррентные списания этим кодом не поддерживаются.

## Точки входа после отдельной согласованной выкладки

Все три функции размещаются на существующей выбранной backend-платформе. Пример ниже обозначает место, **не готовый адрес для заполнения кабинета**:

- `POST <BACKEND>/functions/v1/robokassa-test-create`: Bearer JWT тестового пользователя, JSON `{ "productId": "basic", "idempotencyKey": "<новый UUID>" }`. Продукты: basic, premium, pack100. Передавать свою цену/получателя нельзя. Сохранить UUID до повтора после сетевого сбоя; не создавать новый заказ вслепую.
- Ответ создания: invoiceId, mode=test, grantsAccess=false и checkout `{action,method,fields}`. Отправить поля POST-формой на фиксированный адрес Робокассы. Receipt уже URL-кодирован для подписи; не декодировать его перед формированием формы и не подписывать заново в браузере.
- `POST <BACKEND>/functions/v1/robokassa-test-result`: основной Result URL, form-urlencoded от Робокассы. Без пользовательского JWT, но с обязательной проверкой SHA256-подписи. Использовать именно ResultURL: ResultUrl2 не присылается в тестовом режиме.
- `GET <BACKEND>/functions/v1/robokassa-test-status?invoiceId=<номер>`: тот же Bearer JWT; только собственный заказ. Возвращает pending, expired либо test_paid, всегда grantsAccess=false.

Тестовый checkout выдаётся на один час. Повтор с прежним ключом после истечения не выдаёт новую форму: возвращается expired; для нового осознанного испытания нужен новый UUID. Одновременно может быть только один pending-заказ месячного тарифа, пакеты учитываются отдельно. Ограничены также три создания в минуту, десять в час и три открытых заказа. Подписанное позднее подтверждение expired-заказа всё равно записывается как test_paid (без выдачи доступа), номер не переиспользуется. Это срок выдачи формы нашим backend, а не обещание запретить ранее полученную форму на стороне Робокассы.

Общий внешний JWT-шлюз должен пропускать ResultURL: при отдельной ручной выкладке этой функции используется `--no-verify-jwt`. Проверка подписи остаётся в обработчике. У create/status проверка пользователя всегда выполняется через auth.getUser, поэтому их также можно выкладывать без legacy gateway JWT-проверки, не снимая внутреннюю авторизацию. Здесь supabase/config.toml и workflows не менялись: автоматического включения нет.

## Серверная конфигурация

Только безопасным вводом на сервере/в панели секретов; не хранить значения в Git, браузерной сборке, логах и переписке:

| Имя | Значение/назначение |
|---|---|
| STAYSEE_PAYMENTS_MODE | По умолчанию disabled; для отдельного испытания test. live всегда отклоняется. |
| ROBOKASSA_TEST_MERCHANT_LOGIN | Идентификатор именно нового магазина: StayseeAI |
| ROBOKASSA_TEST_PASSWORD_1 | Отдельный тестовый пароль №1 |
| ROBOKASSA_TEST_PASSWORD_2 | Отдельный тестовый пароль №2, не равный №1 |
| ROBOKASSA_TEST_USER_IDS | UUID специально разрешённых тестовых аккаунтов, через запятую |
| ROBOKASSA_TEST_ORIGINS | Точные origin тестового интерфейса, без пути/завершающего слеша; не wildcard |
| SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY | Штатные серверные настройки, никогда не передаются клиенту |

В технических настройках магазина выбрать тестовый SHA256 и метод Result URL POST. Рабочие пароли не менять. Ошибочный адрес сайта исправляет поддержка. До подключения проверить допустимость разных доменов сайта/приложения/ResultURL, HTTPS, доступность для Робокассы и отсутствие блокирующей пользовательской авторизации на callback.

Портирование/клонирование тестовой базы не должно переиспользовать номер InvId другого заказа того же магазина. Сохранять журнал/последовательность при переносе либо заводить отдельный тестовый магазин/диапазон номеров; не запускать две независимые базы с одной стартовой последовательностью и одним магазином.

## Обязательные следующие этапы (НЕ реализованы этим изменением)

- Проверка полного внешнего пути в настоящей Робокассе после настройки HTTPS callback и тестовых параметров магазина. Локальный тестовый интерфейс уже добавлен, но выключен по умолчанию и не выложен.
- Боевой журнал и атомарная выдача реального тарифа/пакета; история первой успешной покупки любого из этих продуктов, отменяющая будущее бесплатное возобновление. Тест не считается покупкой.
- Независимые права: оплаченный срок и остаток сообщений. Исчерпание сообщений не закрывает функции до paid_until, докупка не меняет paid_until. Срок пакета и тариф независимы.
- Замки архивных бесед/платных функций, серверное ограничение чтения, фиксирование верхней беседы при окончании доступа; перестановка только на действующем платном тарифе. Изменения сверить с Claude, работающим над моделями и переездом.
- Решение по выбору разовой оплаты/добровольного автопродления, отмене, неуспешным списаниям, остаткам и смене ещё оплаченного тарифа. Не реализовывать скрытое автоматическое списание.
- Срок хранения от последнего посещения кабинета, уведомление за 60 дней, безопасное удаление/отмена удаления при возвращении. Платёжные документы требуют отдельной политики, не каскадного уничтожения вместе с перепиской.
- УСН Доходы / Без НДС подтверждены пользователем. `full_prepayment`/`service` в текущем Receipt — технический **тестовый** пример, не утверждённая бухгалтерская схема. Подтвердить признак расчёта/предмет расчёта для тарифов и пакетов, необходимость второго чека и возвраты до продаж.

Существующее set_user_plan сбрасывает период, а месячная квота сейчас может обновляться без новой оплаты. Поэтому простая замена mode=test на live небезопасна и намеренно невозможна.

### Итог независимого ревью и повторных проверок

Четыре важных замечания исправлены за один проход с пятью тестами, сначала воспроизведшими ошибки, затем прошедшими:

- При reload до перехода к провайдеру можно явно восстановить переход к **тому же** заказу. Ошибка фонового опроса не стирает уже проверенный checkout. Повтор не может подменить сохранённый номер заказа.
- Последняя проверка сессии перед POST ограничена 15 секундами и отменяется при уходе с экрана, смене пользователя или завершении pending. Запоздалый ответ не отправляет форму.
- Ответ с checkout одновременно с terminal status отклоняется. Receipt проверяется по схеме и сумме заказа; исходные подписанные байты не пересобираются, прежнее наименование/цена не сравниваются с сегодняшним каталогом.
- Явные серверные `monthly_order_pending`/`too_many_orders` означают «новый заказ не создан»: можно вернуться к выбору, а не «проверять» несуществующий счёт. Неопределённые сетевые ошибки по-прежнему сохраняют UUID для безопасного повтора.

Итог: **2734/2734 offline**, 0 ошибок; targeted client/panel 12/12; PGlite SQL 9/9; проверка типов и UI-enabled сборка успешны. Browser reload→«Восстановить переход к прежнему заказу»→checkout повторно наблюдался после исправления. Повторное ревью не запускалось; исправления подтверждены регрессионными тестами и полной базой.

Небольшое отложенное замечание: обработанный `payment_test_return=1` пока остаётся в адресе; позднейшее обновление страницы может снова открыть тарифы. Это не меняет статус заказа/права и не запускает оплату. Второе небольшое замечание — устаревшее описание отсутствующего интерфейса — исправлено в этом отчёте.

Принятые границы и риск: фикстура не доказывает приёмку Робокассы; PGlite не доказывает боевой PostgREST или конкурентность разных соединений; независимый reviewer не повторял весь offline/browser проход, результаты принадлежат исполнителю.
