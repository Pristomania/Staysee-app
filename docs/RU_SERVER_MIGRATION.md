# Переезд приложения staysee.ru на новый сервер (российский хостер)

Зачем: сервер 78.17.147.119 жив, но из России до него не достучаться (ни сайт, ни VPN на том же адресе). Приложение держится на одном адресе: сайт плюс прокси `/supabase/`. Новый сервер должен быть чистым, без VPN, у российского хостера (Cloud.ru или другого).

Что подготовлено в репозитории и проверено в чистом Ubuntu 24.04 (контейнер):
- `deploy/ru-server/bootstrap.sh` готовит новый сервер: nginx, certbot, ограниченный пользователь `deploy`, папки, брандмауэр (22, 80, 443), две команды-помощника;
- `.github/workflows/deploy-ru.yml` собирает сайт на GitHub и заливает готовые файлы на новый сервер (на сервере больше не нужны git и npm), запуск только вручную;
- старый сервер и старая выкладка `deploy.yml` не затронуты.

Сначала решить: хостер и размер. Достаточно виртуальной машины 2 ядра, 4 ГБ памяти, диск 40 ГБ, Ubuntu 24.04, публичный адрес IPv4, в группе безопасности открыты порты 22, 80, 443. VPN на ней не ставить.

## Шаги

1. **Создать машину** у хостера. Записать её IP (в командах ниже `IP_СЕРВЕРА`).
2. **Ключ выкладки** (на своём компьютере, в Git Bash):
   ```
   ssh-keygen -t ed25519 -f ~/staysee-deploy-ru -C staysee-deploy -N ""
   ```
3. **Подготовить сервер** (из папки репозитория; если root по SSH закрыт, открыть веб-консоль хостера и вставить содержимое файла вручную):
   ```
   scp deploy/ru-server/bootstrap.sh root@IP_СЕРВЕРА:/root/
   ssh root@IP_СЕРВЕРА "bash /root/bootstrap.sh '$(cat ~/staysee-deploy-ru.pub)'"
   ```
   В конце скрипт печатает отпечаток ключа сервера (строка `SHA256:...`) и проверяет, достаёт ли сервер до Supabase (нужен `HTTP 401` или `200`). **Если Supabase не достаётся, дальше не идти: этот хостер не подходит.**
4. **Записать в GitHub** (команды в папке репозитория; ключ `anon` берётся в Supabase: Settings, API, `anon public`; он публичный):
   ```
   gh secret set RU_HOST --body "IP_СЕРВЕРА"
   gh secret set RU_USER --body "deploy"
   gh secret set RU_SSH_KEY < ~/staysee-deploy-ru
   gh secret set RU_HOST_FINGERPRINT --body "SHA256:...из_шага_3"
   gh variable set STAYSEE_SUPABASE_ANON_KEY --body "ключ_anon"
   ```
5. **Выкладка** (после слияния этой ветки в main, иначе GitHub не видит запуск):
   ```
   gh workflow run deploy-ru.yml
   ```
   Выкладка собирает сайт, заливает его и проверяет `http://staysee.ru` через новый сервер без смены DNS (ответ 200 значит, что работает временный режим только по HTTP).
6. **Переключить DNS** у регистратора: A-записи `staysee.ru` и `www` на новый IP. Старые записи не удалять, а заменить значение; TTL поставить минимальный. Проверка: `nslookup staysee.ru`.
7. **Сертификат** (после того как DNS ответил новым адресом):
   ```
   ssh root@IP_СЕРВЕРА "staysee-issue-cert твоя_почта"
   gh workflow run deploy-ru.yml -f https_check=true
   ```
   Вторая команда включает полную HTTPS-конфигурацию и проверяет главную страницу и прокси к Supabase.
8. **Голосовой ввод.** Файлы модели (около 83 МБ, папка `83bbf6f-large-int8`) лежат только на старом сервере в `/var/www/staysee-voice-model/`. Забрать до отключения старого сервера и положить в такую же папку на новом. Без них не работает только кнопка диктовки.
9. **Проверка с телефона на мобильной сети без VPN**: открыть сайт, войти, написать сообщение.

## Откат

Вернуть прежнее значение A-записей. Старый сервер ничего не потерял, но VPN с него лучше перенести на отдельную машину.

## Что дальше

Модели: после выбора поставщика (Cloud.ru или другой) переключить `staysee-chat` на его API отдельным изменением. База данных: решение по 152-ФЗ и переносу Supabase принимается отдельно, вместе с юристом.
