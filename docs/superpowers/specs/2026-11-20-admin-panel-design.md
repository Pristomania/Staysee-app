# Админ-панель StaySee: проект (20.11.2026)

Статус: ждёт одобрения Насти. Размер работы: проект (три этапа). Строить можно только после одобрения.

## Зачем

Настя (владелец) должна без команд и без помощи агента видеть, что происходит с продуктом и с людьми, и менять базовые вещи. Сегодня это скрипты (`usage-report`, `feedback-report`, `set-technical-plan`, `check-test-account-data`) и запросы к базе, которые запускает агент.

## Что решила Настя (её слова)

- Вариант А: раздел внутри приложения по **закрытому адресу**.
- Вход: **метка «админ» в базе и пароль**.
- Видеть: регистрации, оплаты, оценки (ответов и динамики), расходы, кто на каком тарифе, **время последнего входа в кабинет**, данные по почтам, ошибки.
- Менять: тарифы; **блокировку** человека.
- Рассылки: позже.
- Люди и тестовые аккаунты: «человеком созданные» только её два аккаунта, аккаунт сына и аккаунт для проверки настоящего сайта (почта `stacy…`). Всё остальное тестовые аккаунты.
- Реферальная система нужна, это отдельный проект после первого этапа панели.

## Цели

1. Одна страница ответов на вопросы: сколько людей, кто пришёл, кто платит, кто на каком тарифе, кто когда заходил, что оценили, сколько стоит, что сломалось.
2. Найти любого человека по почте и увидеть про него всё нужное для поддержки.
3. Безопасно менять тариф, лимит, блокировку, и чтобы каждое изменение осталось в журнале.

## Не цели

- Показывать беседы целиком (в коде это закреплено: «Admin UI must not expose message content»). Оценённый ответ с вопросом перед ним и заметка человека показываются, как уже в отчётах.
- Заменять оповещения в Telegram.
- Рассылки, промокоды, объявления (позже).
- Сложные роли: пока один вид доступа, «админ».

## Анти-цели (провал, даже если всё «работает»)

- Любая утечка данных людей через панель или через её серверную часть.
- Блокировка или смена тарифа не тому человеку (поэтому подтверждение и журнал «было → стало»).
- Тестовые аккаунты искажают цифры (регистрации, расходы, ошибки), поэтому считаем отдельно.

## Ограничения (найдены в проекте)

- В приложении нет адресов: экраны переключаются состоянием (`currentScreen`). Веб-сервер уже отдаёт главную страницу на любой путь (`try_files … /index.html`), значит `/admin` откроется, а приложение при старте читает адрес и показывает раздел. Для обычного человека такого адреса «нет»: ему показывается обычное приложение.
- На собственном сервере Supabase (переезд) панель управления Supabase (Studio) не ставится, поэтому панель должна быть нашей.
- Согласий на рекламные письма в базе нет (есть `terms`, `pd_processing`, `images`, `age_18`): до первой рассылки нужно новое согласие. Служебные письма можно без него.
- Оплаты (Robokassa) лежат в ветке Кодекса `codex/robokassa-test-payments-20261119` и не слиты. В основной ветке есть только пакеты сообщений.
- Готового механизма блокировки нет. У Auth есть `banned_until`, но уже выданные входы живут до часа, поэтому блокировка = запрет входа + закрытие входов + отказ в ответе чата.
- Сегодня в базе 12 аккаунтов (на 20.11): шесть на адресах `.invalid` (тестовые), два на `staysee.invalid` (технический аккаунт премиум со 114 беседами и аккаунт без бесед), остальные четыре почтовые, их распределение (кто из них Настя, сын, аккаунт проверки) подтверждает Настя.

## Подходы

- **А. Раздел `/admin` внутри приложения** (выбран Настей). Данные только через серверную функцию с проверкой админа. Едет вместе с приложением на российский сервер; один дизайн и одни тексты. Минус: пишем сами.
- **Б. Отдельный сайт со своим входом.** Безопаснее по отделению кода, но вдвое больше выкладок; сейчас избыточно. Отклонён.
- **В. Готовые инструменты (графики/таблицы).** Быстро для графиков, но не делают наши действия безопасно (блокировка, тариф, письма), и данные людей уходят к стороннему сервису (152-ФЗ). Отклонён.

## Решения (мои, проверить при чтении)

1. **Метки аккаунтов.** Отдельная таблица меток (не колонка в `profiles`, чтобы не трогать живую таблицу): `owner` (Настя), `family`, `checker` (проверка настоящего сайта), `technical` (тестовые), `person` (настоящие люди), по умолчанию «не отмечен». Панель по умолчанию показывает только `person`/`owner`/`family`/`checker`, тестовые скрыты, переключатель «показать все». Цифры считаются отдельно для людей и для тестовых. Метки ставит Настя в панели; первую разметку 12 аккаунтов я предложу по почтам, она подтвердит.
2. **Вход.** Таблица `admin_users`. Обычный вход в аккаунт, затем при открытии `/admin` повторный ввод пароля; доступ живёт 30 минут без действий, потом снова пароль. Сервер проверяет не только отметку, но и что пароль введён недавно (время способа входа в самом токене). Одноразовые коды (второй фактор) добавим позже по желанию.
3. **Серверная часть.** Одна функция `admin-api` (с ключом службы) проверяет админа и свежесть пароля и вызывает функции базы, доступные только службе. Браузер к чужим данным напрямую не ходит; правила доступа (RLS) обычных таблиц не меняются.
4. **Журнал.** Каждое изменение админом пишется в таблицу журнала: кто, когда, что, было → стало. Только добавление, без правки и удаления. В журнале идентификаторы людей, не почты.
5. **Данные для поддержки.** Почты в панели показываются полностью (нужно для поддержки), в журналах нет.
6. **Блокировка (этап 2).** Запрет входа + закрытие входов + отказ в ответе чата с понятным сообщением; снимается; всегда с подтверждением и записью в журнал.
7. **Ошибки.** Берём из журнала расходов (коды ошибок моделей) и из таблиц ошибок и оповещений памяти; Telegram-оповещения остаются как есть.
8. **Страницы по 50 строк**, поиск по почте точный и по началу, даты московские.

## Этапы

1. **Смотреть.** Люди (список, поиск по почте, метки, карточка человека: регистрация, **последний вход**, тариф, согласия, расход за 30 дней, оценки, ошибки), тарифы (сколько людей на каком), оценки ответов и динамики (с заметками), расходы (по дням, людям, беседам), ошибки.
2. **Менять.** Блокировка и разблокировка, смена тарифа, лимиты, пакеты сообщений, письмо для сброса пароля, метки, выгрузка и удаление данных человека по его просьбе (152-ФЗ), журнал.
3. **Позже.** Оплаты (после слияния ветки Кодекса), рассылки (после нового согласия), промокоды, плашка «технические работы», реферальная система (отдельный проект).
