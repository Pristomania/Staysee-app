# StaySee AI: серверная выдача оплаченного доступа

Продолжение согласованного проекта 19.11.2026; пользователь подтвердил порядок 20.11.2026. Дополнение пользователя: **покупка тарифа завершает пробный остаток; простая докупка его сохраняет**. Любая успешная настоящая покупка навсегда отключает последующие бесплатные возобновления.

## Граница этапа

Реализовать серверную модель и локальную SQL-приёмку без активации настоящих платежей, без production/секретов/внешних запросов и без изменений моделей/памяти/копии Claude. Добавочная миграция после тестовой094. Тестовые заказы и их callback не выдают прав и не меняют историю реальных покупок. Миграцию не применять в бою до всех следующих этапов (счётчик UI, замки и внешняя приёмка). Нет разрешения на commit/push/deploy.

## Подходы

Существующий set_user_plan сбрасывает период, а quota автоматически обновляется каждые30 дней; простой вызов после callback небезопасен. Отдельный сервис/БД дублирует текущую базу и не нужен. Выбран добавочный PostgreSQL журнал боевых заказов и атомарная сервисная операция подтверждения/выдачи, с минимальными полями происхождения/срока в usage. Это инженерный выбор внутри согласованного подхода, не новый платёжный сервис.

## Правила

- Месячный продукт только basic1990₽/400 или premium4900₽/1000, пакет pack100590₽/100, 12 календарных месяцев. Цены только серверные. Первая покупка тарифа возможна с free/истёкшего purchased тарифа. Во время действующего либо ручного платного доступа не продавать новый месячный тариф; смена/досрочное продление отдельно. Пакет можно покупать при любом tier.
- paid_until = время серверного подтверждения +30 суток. Месячная выдача обнуляет счётчики периода/дня как начало нового оплаченного периода, не unlimited, suspension, override. Первоначальный бесплатный остаток завершается: после истечения free с нулём бесплатных сообщений. Пакет никогда не вызывает set_user_plan, не меняет tier, срок, период/его счётчик или существующие пакеты.
- Срок и сообщения независимы. До paid_until при нуле сообщений функции тарифа остаются. После срока effective tier=free; оставшиеся действующие пакеты сохраняются, не открывают функции. При отказе/возврате не выводить неизвестную политику: возврат/восстановление пробных сообщений этим этапом не реализованы.
- usage получает источник доступа manual/purchase (manual по умолчанию), paid_access_until и first_real_purchase_at. Никаких массовых изменений существующих tier/счётчиков. Ручные/семейные/технические назначения и unlimited не превращать в покупки и автоматически не снимать. Прямое чтение stale tier не должно дать серверу платные функции: rate check вычисляет effective tier по серверному времени; quota дополнительно атомарно завершает purchased период под блокировкой usage.
- Ручной set_user_plan явно возвращает источник manual, очищает текущий purchased срок, но не историю реальной покупки. Историю не сбрасывать сменой tier/unlimited/периода. Техническая выдача пакета существующим grant_message_pack не считается реальной покупкой.
- Обновление месячной квоты по времени сохраняется только для старых manual назначений. Бесплатное idle-обновление только при first_real_purchase_at IS NULL. После тарифа free used50, без новых50; докупка на free сохраняет первоначальный stored used/period. Счётчик клиента с этими полями и замки — следующий отдельный проход; не выкладывать только половину правил.

## Журнал и атомарность

Сервисный billing_live_orders: UUID, invoice identity (отдельный от test диапазон2e12), nullable user FK SET NULL, merchant, product, сумма в копейках/снимок названия, idempotency UUID, created/expires/paid/applied, статус pending/applied/paid_unfulfilled, reason. RLS, никаких прямых прав authenticated/anon. Минимальный журнал переживает удаление auth, без email/переписки/карт. Аккаунт usage удаляется как раньше. Явно включаемый live-create gate в отдельной защищённой таблице по умолчанию false.

Create: gate, пользователь активен/не suspended/не удаляет комнату, каталог, UUID, один pending месячный, TTL1h и лимит3/min10/hour3pending; одинаковый ключ возвращает тот же заказ/снимок, другой продукт конфликт. Checkout/подпись/боевой внешний callback ещё НЕ подключаются. Публичных функций оплаты этим этапом нет.

Builder check выявил один крайний случай, решён автором: TTL запрещает продолжать старый checkout, но **не отменяет настоящую оплату**. Позднее подтверждение записывается и выдаёт доступ по обычной проверке eligibility; при конфликте/удалении — paid_unfulfilled. Иначе можно было бы потерять реально принятые деньги. Нужен отдельный тест.

Confirm-and-apply(p_order_id,p_amount_kopecks) только service_role: будущий адаптер обязан до вызова проверить настоящую подпись/merchant/номер/режим. Не доверяет пользовательскому утверждению об оплате. Все изменения одной транзакцией, порядок блокировок **usage → order → pack**, чтобы совпасть с quota/create; после ожидания перечитать статус. Совпавший повтор возвращает прежнее состояние без нового grant/сдвига срока. Сумма должна точно совпасть даже при повторе. Тестовые номера/UUID другого журнала не принимаются. Временное отключение создания заказов не теряет подтверждения уже существующего заказа.

Review уточнил: create/confirm не вызывают изменяющее завершение срока. Для покупки тарифа eligibility вычисляется по исходному сроку под блокировкой; для пакета истечение не нужно вообще. Повтор сначала проверяет сумму/locked status и выходит без мутаций usage. Истечение выполняет quota/явная сервисная синхронизация, не повтор уведомления пакета.

Защитный потолок расходов сохраняется, но финансирование и доступный остаток пакетов учитываются раздельно. В пределах периода уже израсходованный пакет сохраняет свою долю финансирования — иначе новый оплаченный пакет мог быть полностью заблокирован старым расходом. При смене периода для переносимого пакета единожды фиксируется доля по оставшимся сообщениям; старые израсходованные пакеты не увеличивают новый потолок. Снимок бюджета хранится в дополнительных сервисных полях пакета и не уменьшается при каждом списании сообщения. Финансовую политику возврата/void до настоящих продаж требуется отдельно согласовать и увязать с этим учётом; автоматического live возврата нет.

Права сбрасываются явно даже для service_role, включая identity sequence и возможные permissive default ACLs. Прямые изменения реального журнала/последовательности запрещены; service читает журнал и меняет только create_enabled настройки, выдача только фиксированными RPC. Реальную историю не удалять правом «очистки тестовых фикстур».

Два разных оплаченных месячных заказа: первый выдаёт доступ, второй paid_unfulfilled reason active_plan; срок/счётчики первого не затирать. Удалённый/заблокированный аккаунт либо ручное платное назначение после создания заказа: paid_unfulfilled, без воскрешения профиля/usage. paid_unfulfilled — сохраняемый факт оплаты для будущего ручного разбора, не скрытое начисление. История первой реальной оплаты ставится и для активного аккаунта с paid_unfulfilled (деньги реально приняты), но отсутствующий usage не восстанавливается. Package grant использует payment_ref='robokassa-live:'+orderUUID; не считать ручной/test grant покупкой.

## Проверки

Настоящий локальный PostgreSQL PGlite с минимальными auth/usage/profiles/limits/logs и актуальными085–090 функциями. Проверить default-off gate и права, цены/повторы/лимиты/TTL, подтверждение+30days, израсходованные сообщения до конца, пакет без сброса, истечение и пакеты на free, отсутствие free-renew у платившего и сохранение у never-paid, manual/unlimited unchanged, второй реальный платёж, inactive/deleted, rollback после сбоя pack, удаление auth FK, точную сумму, тестовую изоляцию. Это не full Supabase/PostgREST/отдельные concurrent соединения; не выдавать queued PGlite за доказательство настоящих гонок. Для атомарности блокировок ещё нужен отдельный multi-connection local test до live.

Полная offline база, typecheck, Deno, чистый diff-check. Независимое review новой модели и SQL; никаких платных/модельных/боевых тестов. В отчёте отдельно указать непроверенные UI, locks, provider, full local Supabase. До live согласовать бухгалтерские признаки/чеки, правила возврата/смены и проверить внешнюю интеграцию.
