# Повышение действующего тарифа — уточнение пользователя20.11

Одобрено пользователем: действующий basic («Стандарт» в речи пользователя; текущий код называет его «Базовый») можно заменить на premium по полной текущей цене Premium, с новым сроком30дней с подтверждения оплаты. Старый включённый остаток не переносится и не складывается; отдельно докупленные сообщения сохраняются с прежним остатком/сроком, не становятся бессрочными и не открывают платные функции сами по себе.

Подход: минимальная новая миграция100 расширяет только серверные create/confirm из095/099. Не выдавать второй параллельный тариф/квоту, не делать доплату/пропорциональный возврат: эти альтернативы противоречат выбранной полной покупке и замене. Действующий purchased basic→premium разрешён; basic→basic, premium→premium/ basic до окончания периода не разрешены. Ручные/семейные/unlimited планы не превращать в покупки автоматически. После истечения обычная новая покупка остаётся возможна. Если между заказом и подтверждением уже включён другой Premium/ручной тариф или аккаунт удалён/заблокирован, учесть деньги как paid_unfulfilled, а не повторно выдавать права. Перепроверять состояние под usage/order locks; повтор заказа/подтверждения безопасен.

Подтверждение Premium использует уже существующую выдачу: один tier, новый paid_access_until, period_used=0 и новые счётчики периода. Пакеты не обновлять/не удалять, first_real_purchase_at не сдвигать, free50 не возвращать. Пост-lock clock сохранить; create тоже захватывает его после usage lock, чтобы eligibility не зависела от начала длинной транзакции. Прайс остаётся серверным premium490000коп., никакой клиентской скидки.

Уточнение после ревью: закрытый ledger хранит purchase_kind=new_period/upgrade, чтобы отличать ожидающее повышение от первой покупки. Ручной перевод ожидающего повышения даже на free возвращает paid_unfulfilled/manual_access; первая покупка на manual/free и естественное истечение purchased допускаются. Новым заказам явно записываются created_at=v_now и expires_at=v_now+1час: DEFAULT now() от начала транзакции сокращал бы срок checkout после ожидания. Сигнатуры RPC не меняются.

Только локальные SQL и тесты, без включения checkout/UI/магазина/боевой базы, без коммитов. Текущие callback/test транспорты не менять. Процент скидки, автопродление, возврат за старый срок не добавлять.
