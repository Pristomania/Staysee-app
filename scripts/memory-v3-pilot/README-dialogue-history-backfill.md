# Разбор истории переписки по диалогам (Memory V3) — инструкция для Насти

Простыми словами: это разовый инструмент, который берёт всю историю переписки
и прогоняет её через нейросеть, чтобы вытащить устойчивые факты и темы — но,
в отличие от уже опробованного инструмента "по всей истории целиком"
(`lifecycle-history-backfill-*`), этот раскладывает результат **по каждому
диалогу отдельно**. Технику разбора не трогали — переиспользовали то, что уже
проверено; переделали только группировку по диалогам.

Инструмент ничего не запускает сам по себе и ничего не пишет в боевую память
автоматически. Каждый шаг ниже — это отдельная команда, которую нужно
запустить руками (или попросить Cursor запустить руками) и явно посмотреть
на результат, прежде чем переходить дальше.

## ⚠️ Прочитай перед тем, как что-то запускать

1. **Это стоит настоящих денег.** Один из шагов ниже — это реальные платные
   запросы к нейросети через OpenRouter. Все остальные шаги денег не тратят.

2. **Это ЗАМЕНЯЕТ, а не дополняет память.** Если в каком-то диалоге уже
   что-то накопилось само по себе (за счёт того, что функция памяти по
   диалогам недавно включена и работает вживую) — этот разбор **полностью
   заменит** там старые записи новыми, а не пропустит такой диалог и не
   добавит к старому. Это сделано специально, по твоей же просьбе — сравнить,
   что выдаёт разбор истории, с тем, что уже накопилось само. Но это значит:
   **перед переносом в боевую память обязательно прочитай отчёт** (шаг 3
   ниже) — там по каждому диалогу прямо написано, была ли там уже своя
   память и заменяется ли она. Если по какому-то диалогу результат разбора
   выглядит хуже или подозрительнее того, что там уже было — для этого
   диалога перенос просто не делать.

3. **Перед первым переносом проверь миграции в базе** — подробности в
   разделе "Проверка миграций" ниже. Если пропустить, перенос сразу
   нескольких диалогов может отработать наполовину и показать общую ошибку,
   не объяснив, что часть диалогов на самом деле уже обновилась.

## Что нужно, чтобы начать

- Файл `.env` в корне проекта с четырьмя строками: `SUPABASE_URL`,
  `SUPABASE_SERVICE_ROLE_KEY`, `STAYSEE_MEMORY_V3_BACKFILL_USER_ID` (тот же
  аккаунт, что и в прошлый раз для разбора по всей истории целиком),
  `OPENROUTER_API_KEY`.
- Свежий файл с текущими ценами на модель (не старше суток) — его готовит
  тот, кто технически запускает разбор (Cursor), формат тот же, что и для
  прошлого разбора по всей истории.
- Все команды ниже — это **реальные, работающие** названия файлов и флагов,
  проверенные по актуальному коду на момент написания этой инструкции. Не
  меняй в них ничего "на глаз" — особенно флаг `--profile` (см. отдельное
  предупреждение перед шагом 2).

В примерах команд ниже используется один и тот же условный путь для файла
результата — `C:\stay-backfill\dialogue-history-backfill.json`. Замени его
на свой; главное требование — путь должен быть абсолютным. Этот файл (и всё,
что рядом с ним появится) содержит личные данные и **не должен** попадать в
git: либо храни его вне папки проекта (как в примере), либо, если запускаешь
из папки проекта, назови файл с префиксом `scripts/tmp-` — такие файлы в
этом проекте уже настроены как "не для git".

## Проверка миграций (сделать один раз, до первого переноса)

Для этой функции появились две новые миграции, и порядок важен:

- `20260924150000_050_memory_v3_dialogue_backfill_import.sql`
- `20260924160000_051_memory_v3_dialogue_backfill_import_conversation_scope.sql`
  — это исправление ошибки в предыдущей миграции: без неё перенос
  **нескольких диалогов подряд за один раз** работает неправильно.

Обычный способ деплоя (`npx supabase db push`) должен подхватить обе
автоматически — они оформлены как обычные файлы миграций с правильными
датами по порядку. Но перед тем, как переносить несколько диалогов сразу,
стоит явно проверить, что **обе** миграции применились. Если 051 не
применится, перенос не выдаст явную понятную ошибку — он просто молча
остановится после первого же успешно перенесённого диалога с общей ошибкой,
и может показаться, что не перенеслось вообще ничего, хотя один диалог на
самом деле уже обновился в базе. Поэтому — сначала проверить, потом
переносить несколько диалогов за раз.

## Шаг 1. Пробный запуск без денег

Ничего не тратит и не пишет в боевую память. Делает запросы к базе только
на чтение (включая проверку текущего состояния памяти по каждому диалогу —
это не ошибка и не опасно, просто раньше это не требовалось).

```
npx tsx scripts/memory-v3-pilot/dialogue-history-backfill-run.ts --inspect-source --profile memory-v3-lifecycle-history-backfill-v1 --source-cutoff <ДАТА-СРЕЗА> --price-snapshot-file <ПУТЬ-К-ФАЙЛУ-С-ЦЕНАМИ.json> --max-budget-usd <ПОТОЛОК-БЮДЖЕТА>
```

Про плейсхолдеры:

- **`<ДАТА-СРЕЗА>`** — момент времени, позже которого сообщения не
  участвуют в разборе. Формат строгий: `ГГГГ-ММ-ДДTЧЧ:ММ:ССZ`, например
  `2026-09-24T23:59:59Z`. Просто дата без времени (`2026-09-24`) инструмент
  не примет. Подробнее — в разделе "Про дату среза" ниже.
- **`<ПУТЬ-К-ФАЙЛУ-С-ЦЕНАМИ.json>`** — абсолютный путь к файлу с ценами,
  который приготовил технический помощник. Он должен быть не старше суток
  на момент запуска — и на пробном, и на платном шаге, так что если между
  ними прошло больше суток, файл нужно обновить перед платным запуском.
- **`<ПОТОЛОК-БЮДЖЕТА>`** — максимальная сумма в долларах, которую вы
  разрешаете потратить (просто число, например `5.00`, без знака `$`).

Готовой суммы в долларах этот пробный запуск на экран не печатает — он
только проверяет, что всё настроено правильно, и печатает технический номер
`sourceSnapshotDigest`, который понадобится для следующего шага. Чтобы
прикинуть, какой потолок бюджета разумен: если указанный `<ПОТОЛОК-БЮДЖЕТА>`
окажется слишком маленьким для реального объёма переписки, пробный запуск
сразу откажет с ошибкой (без денег и без обращения к нейросети) — тогда
можно смело увеличить число и попробовать снова.

**Скопируй из вывода команды значение `sourceSnapshotDigest`** — оно
понадобится дальше как есть, без изменений.

### ⚠️ Про флаг `--profile` — не пугайся и не исправляй

Команда просит написать `--profile memory-v3-lifecycle-history-backfill-v1`
— со словом **lifecycle** внутри, хотя весь этот инструмент про диалоги, а
не про lifecycle. **Это не ошибка и не опечатка.** Техническая часть,
отвечающая за лимиты запроса к нейросети и цены, была переиспользована без
переименования от старого инструмента. При этом результат разбора везде
правильно помечен как `profileId: memory-v3-dialogue-history-backfill-v1` —
то есть сам итог посчитан и подписан правильно для диалогового инструмента,
просто название технического профиля в команде выглядит "от другого
инструмента". **Если кто-то технический захочет "поправить" эту строку на
что-то со словом dialogue — не надо: тогда команда перестанет работать
вообще**, она проверяет именно эту точную строку. Эта же строка нужна и
в следующем, платном шаге.

## Шаг 2. Настоящий платный запуск

Только теперь тратятся деньги. Используй ТОТ ЖЕ `--source-cutoff`, что и в
шаге 1, и `sourceSnapshotDigest` из его вывода:

```
npx tsx scripts/memory-v3-pilot/dialogue-history-backfill-run.ts --execute-history-backfill-paid-requests --profile memory-v3-lifecycle-history-backfill-v1 --source-cutoff <ТА-ЖЕ-ДАТА-СРЕЗА> --expected-source-sha256 <sourceSnapshotDigest-ИЗ-ШАГА-1> --price-snapshot-file <ПУТЬ-К-ФАЙЛУ-С-ЦЕНАМИ.json> --max-budget-usd <ПОТОЛОК-БЮДЖЕТА> --safe-output-file C:\stay-backfill\dialogue-history-backfill.json
```

`--safe-output-file` — обязательно абсолютный путь, обязательно
заканчивается на `.json` (см. предупреждение про личные данные выше).

Если команда прошла успешно, **рядом с этим `.json`-файлом автоматически
появится второй файл с тем же именем, но расширением `.txt`**
(`C:\stay-backfill\dialogue-history-backfill.txt` в примере выше) — это и
есть человекочитаемый отчёт по-русски из шага 3. Отдельно ничего для этого
запускать не нужно.

## Шаг 3. Обязательно прочитать отчёт до переноса

Открой `.txt`-файл, который появился рядом с `.json` на предыдущем шаге.
В нём по-русски, по каждому диалогу:

- сколько всего диалогов разобралось и сколько из них уже имели свою память
  (и значит — будут заменены);
- какие факты и темы нашлись в каждом диалоге;
- какие диалоги не удалось разобрать (если такие есть).

**Именно на этом шаге нужно решить**, всё ли выглядит разумно. У инструмента
пока нет команды "перенести только один диалог" — перенос делается сразу по
всем диалогам из файла, поэтому решение "переносить или нет" нужно принять
по отчёту целиком, до следующего шага.

## Шаг 4. Собрать файл-подтверждение переноса

Ничего вручную писать не нужно — файл собирается автоматически из уже
готового результата:

```
node --import tsx scripts/memory-v3-pilot/dialogue-history-backfill-approval.ts --generate-approval --artifact-file C:\stay-backfill\dialogue-history-backfill.json
```

Рядом появится файл `dialogue-history-backfill.review.json` (имя
подставляется автоматически, менять его не нужно) — в консоли также
выведется его точный путь.

## Шаг 5. Настоящий перенос в боевую память

Это последний и по-настоящему необратимый шаг — он меняет боевые данные. У
этой команды другое правило для переменных из `.env`: она читает их не из
самого файла `.env`, а из окружения запуска, поэтому `.env` нужно явно
подключить флагом `--env-file`:

```
npx tsx --env-file=.env scripts/memory-v3-pilot/dialogue-history-backfill-import-run.ts --import-reviewed-history --artifact-file C:\stay-backfill\dialogue-history-backfill.json --review-file C:\stay-backfill\dialogue-history-backfill.review.json --import-id <НОВЫЙ-СЛУЧАЙНЫЙ-UUID>
```

`<НОВЫЙ-СЛУЧАЙНЫЙ-UUID>` — просто новый случайный идентификатор для этого
конкретного запуска переноса (не диалога); технический помощник может
сгенерировать его одной командой.

В выводе будет список диалогов и статус по каждому: `succeeded` — перенос
удался, `rejected_state_changed` — не удался для этого одного диалога.

### Если какой-то диалог получил статус `rejected_state_changed`

Это значит: что-то в этом диалоге поменялось уже после того, как платный
разбор (шаг 2) зафиксировал его начальное состояние — например, туда
пришло новое сообщение. Перенос для этого диалога сработал безопасно:
**ничего в нём не сломал и не заменил** — просто отказался, чтобы не
перезаписать свежие данные устаревшим разбором. Все остальные диалоги из
того же переноса переносятся нормально, один отказ не останавливает
остальные.

Чтобы всё-таки перенести и этот диалог — нужно заново пройти весь путь
(шаги 1–5) ещё раз: инструмент пока не умеет выбирать для повторного
разбора только один диалог, повторный разбор снова пройдёт по всей истории.
Диалоги, которые уже успешно перенеслись в прошлый раз, можно не переносить
второй раз — это будет лишний, ненужный платный расход.

## Про дату среза (`--source-cutoff`) чуть подробнее

Дата среза "замораживает" список сообщений на точный момент времени — всё,
что придёт в диалог позже этого момента, просто не попадёт в разбор. Это
специально сделано для диалогов, где переписка продолжается прямо сейчас
(например, для самого активного, постоянно растущего диалога): без даты
среза, если между разбором (шаг 2) и переносом (шаг 5) пройдёт несколько
дней и в диалог придёт что-то новое, перенос для этого диалога честно
откажет с `rejected_state_changed`, а не перезапишет память старыми
данными поверх новых. Указывать дату среза "с запасом" (например, конец
сегодняшнего дня) — нормальная и рекомендуемая практика, особенно для
такого диалога.

## Коротко: что за какой файл отвечает

| Файл | Что делает | Тратит ли деньги |
|---|---|---|
| `dialogue-history-backfill-run.ts` | пробный разбор (`--inspect-source`) и настоящий платный разбор (`--execute-history-backfill-paid-requests`) | только `--execute-history-backfill-paid-requests` |
| `dialogue-history-backfill-report.ts` | не запускается вручную — им автоматически пользуется `-run.ts`, чтобы создать `.txt`-отчёт | нет |
| `dialogue-history-backfill-approval.ts` | собирает файл-подтверждение из готового результата разбора | нет |
| `dialogue-history-backfill-import-run.ts` | настоящий перенос проверенного результата в боевую память | нет (сам перенос бесплатный, деньги уже потрачены на шаге 2) |

Реальный платный разбор и реальный перенос в боевую память **не запускались**
в рамках этой задачи — это осознанно оставлено как отдельный шаг для Насти
(или для того, кому она это доверит), по этой инструкции.
